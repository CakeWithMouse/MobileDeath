# Асинхронная загрузка

Реализовано 29.10.2026 в пределах запуска приложения и существующей смены. Баланс, обучение и остальные игровые настройки не переносились в JSON.

## Жизненный цикл

`AppBootstrap` сначала показывает постоянный `LoadingScreen` без ссылок на игровой контент и даёт ему два кадра. Затем:

1. Асинхронно читает `Resources/Loading/loading.json`, проверяет схему и обязательные поля.
2. Через `Resources.LoadAsync<LoadingCatalog>` загружает каталог и разрешает текстовый ключ контента. В `Bootstrap.unity` тяжёлая ссылка `content` обнулена; `Gameplay.asset` не загружается вместе со стартовой сценой.
3. `FileGameStore.PrefetchAsync` читает основной и резервный файлы в фоновом потоке. JSON, проверка схемы и Unity API выполняются на главном потоке. Снимок чтения освобождается после `Load`, последующие проверки записанного файла читают актуальный диск.
4. Создаёт контроллер с отложенным восстановлением. `RestoreSteps` воспроизводит журнал порциями не более 32 команд, также уступая кадр при достижении бюджета 4 мс. Полная сессия публикуется после успешного воспроизведения; неверная команда не записывает частичный результат. Синхронный конструктор сохранён для существующих клиентов и проверок.
5. Асинхронно открывает `Cafe`, проверяя наличие сцены в сборке. При повторе после ошибки уже открытая сцена используется повторно.
6. `GameView.InitializeAsync` строит атлас по текстурам и позам; расчёт вариантов поджаривания уступает кадр каждые 16 строк. Затем по кадрам создаются группы интерфейса. Во время работы симуляция не обновляется, загрузочный слой перекрывает ввод.
7. Открывает главное меню с восстановленной сменой на паузе и убирает загрузочный экран.

Кнопки начала/продолжения смены, повтора и возврата в главное меню идут через тот же координатор. Повторный запуск перехода блокируется. Перед операцией рисуется экран, `GameView` выключает обновление симуляции и взаимодействие Canvas, освобождает захваченный указатель. Затем выполняется реальное действие, при включённом флаге ожидается `Resources.UnloadUnusedAssets`, и возвращается управление. Результат смены по-прежнему появляется обычным игровым переходом; экран загрузки сопровождает выход с результата в меню.

Отдельной сцены «матч» нет: смена является сессией Domain, а кафе и меню используют общие графику, атлас и UI. Они намеренно сохраняются для продолжения незавершённой смены. При выходе из завершённой смены очищаются кэши движений и ссылок на блины. Временные текстуры подготовки атласа освобождаются в `finally`; сам атлас освобождается при уничтожении представления. Перезагрузка сцены ради каждой смены не добавлена.

## Конфиг и ресурсы

Файлы в `UnityPart/PancakeCooker/Assets/Blinopek/Resources/Loading`:

- `loading.json`: `schema: 1`, имя сцены `scene`, стабильный текстовый `contentKey`, флаг очистки `unloadUnusedAssets`, минимальная длительность `minimumVisibleSeconds` (по умолчанию 1 секунда).
- `catalog.asset`: ScriptableObject `LoadingCatalog`, соответствие уникального ключа `cafe.default` существующему `GameContent`. Уже существующий `GameContent` содержит ссылки на тяжёлую графику, шрифты, шейдеры и звуковую библиотеку; его `artwork` сопоставляет текстовые ключи иллюстрациям. JSON не содержит путей к текстурам и Unity GUID.

Каталог проверяет пустые и повторяющиеся ключи, отсутствующие ссылки и неизвестный запрошенный ключ. `Blinopek → Prepare gameplay scenes` создаёт/обновляет запись `cafe.default`, сохраняя другие записи каталога. JSON входит в сборку как локальный TextAsset. Для смены конфигурации нужна пересборка; удалённая доставка и Addressables не входят в эту задачу.

## Ошибки

Исключения загрузки остаются на экране с сообщением и кнопкой «Повторить»; подробности пишутся в Unity log. При ошибке перехода доступно «Вернуться», чтобы снять блокировку ввода. Ошибки файлового сохранения по-прежнему отображаются существующим интерфейсом хранилища. Повреждённый/несовместимый файл блокирует начало смены и перезапись; загрузочный экран не удаляет прогресс и не выполняет автоматический сброс.

- Все runtime- и Editor-исходники скомпилированы против библиотек установленной Unity 6000.6.5f1 через отдельный временный .NET-проект: 0 ошибок, 0 предупреждений. Это проверка C#, не Unity import/build или IL2CPP.
- `Tools/LoadingValidation.cs` вместе с `Tools/MenuNavigationValidation.cs` предназначены для папки Editor в изолированной копии проекта. Запуск: Unity `-batchmode -quit -projectPath <копия> -executeMethod LoadingValidation.Run -logFile <лог>`. Проверяются загрузочный JSON/каталог, неизвестный ключ, порционное создание GameView, монотонность прогресса и начало смены через координатор, затем существующие сценарии навигации. Первоначальный CLI-запуск не подключился к `LicenseClient-swag_` (IPC refused / licensing initialization failed). После активации лицензии проект успешно запущен через Unity Hub в установленной Unity 6000.6.5f1; проверки выполнены в открытом редакторе, поскольку CLI-среда продолжила получать отказ IPC. Проверки LoadingValidation прошли, MenuNavigationValidation прошёл 68 проверок для успешного и неуспешного дня. Тест закрытия смены актуализирован: принятый заказ должен дождаться истечения терпения и ухода гостя. Каждый запуск LoadingValidation получает уникальное временное сохранение.
- Процент показывает взвешенный прогресс этапов и порций, а не оставшееся время. Чтение файлов вынесено в фон; Unity API остаётся на главном потоке. JSON-десериализация, одна команда журнала, GPU readback одной текстуры, финальный `PackTextures`, создание отдельной группы UI и атомарные записи сохранения остаются неделимыми операциями. Гарантия 60 FPS без профилирования на устройстве не заявляется.
- Перед приёмкой на устройстве проверить холодный запуск, длинный журнал, повреждённые основной/резервный файлы, старт/продолжение/повтор смены, возврат с результата и из паузы, фон/фокус во время загрузки, отсутствие двойных запусков от повторного нажатия, читаемость экрана и максимальное время кадра в Profiler.


### Подтверждённый запуск в Unity (29.10.2026)

`Tools/LoadingRuntimeValidation.cs` проверяет полный Bootstrap в Editor Play Mode. Для повторения скопировать его вместе с LoadingValidation.cs и MenuNavigationValidation.cs в папку Editor, создать `%TEMP%/blinopek-runtime-result/run.flag` и обновить Assets. После завершения убрать эти временные копии из Assets. В исходном проекте временные скрипты уже убраны.

Пройдены 16 проверок: холодный запуск с видимым загрузочным экраном на нескольких кадрах и выходом в свежее меню; блокировка обновления/Canvas при старте; создание смены; возврат в меню с сохранением сессии; продолжение того же объекта сессии; повтор дня с заменой сессии; искусственная ошибка перехода; успешный повтор; возврат после повторной ошибки с восстановлением ввода. Дополнительно проверена монотонность прогресса холодного запуска. Кадр `Подготавливаем кухню — 63%` просмотрен; полоса прогресса получила контрастное золотистое заполнение и повторно проверена.

Сохранение изолируется одноразовым `AppBootstrap.EditorValidationSavePath` (только UNITY_EDITOR): путь сбрасывается после чтения Bootstrap и не попадает в player. Проверки используют отдельные JSON в `%TEMP%/blinopek-runtime-result`. Настройки Play Mode пользователя (включая отключённый Domain Reload) сохраняются; прежняя стартовая сцена редактора восстанавливается. Искусственные ошибки записываются в Console как ожидаемая часть проверки.

Это реальный запуск в редакторе с обычными ресурсами проекта, не standalone/Android/IL2CPP-проверка. Отдельный процесс player, восстановление после полного закрытия приложения, фон/фокус на телефоне и бюджет кадров на целевом устройстве в этой проверке не подтверждены.


### Минимальное время и плавный прогресс (29.10.2026)

В loading.json задано minimumVisibleSeconds: 1; значение по умолчанию в C# и резервное значение Bootstrap также равны 1 секунде. Допускается только конечное неотрицательное число; 0 отключает искусственный минимум. Отсчёт начинается в LoadingScreen.Show по Time.realtimeSinceStartupAsDouble. Реальные операции начинаются сразу после штатных кадров отрисовки экрана. Coroutine ждёт лишь оставшуюся часть минимума, без блокировки главного потока и без дополнительной обязательной секунды после долгой работы. Игровые паузы и timeScale на этот отсчёт не влияют.

ActualProgress и DisplayedProgress разделены. Report сохраняет монотонный фактический отчёт; Update сглаживает его по unscaledDeltaTime и ограничивает раннее отображение временем от Show. Пока работа не завершена, полоса следует реальным отчётам: она не движется к 99% только из-за истечения минимальной секунды. Если реальный прогресс стоит на 10%, сглаженное отображение тоже остаётся около 10% до следующего отчёта. Временные веса этапов и графических порций остаются приблизительной оценкой работы, а не точным процентом прочитанных байтов.

После завершения быстрой работы Complete запоминает уже показанное значение и плавно распределяет оставшееся заполнение на остаток минимальной секунды. Если работа дольше минимума, дополнительной секундной анимации не возникает. Когда работа завершена и минимум истёк, выставляются ReadyToClose и 100%; один финальный кадр даёт отрисовать завершённое состояние, после чего Guard закрывает экран и возвращает ввод. Целочисленная подпись до ReadyToClose ограничена 99%, чтобы округление не создавало ранние 100%.

Этот механизм применяется к холодному запуску, старту/продолжению/повтору смены, меню и повторной попытке. Ошибка показывается сразу и замораживает достигнутый прогресс. Повтор начинает новый отсчёт и заполнение; возврат после ошибки ждёт лишь остаток минимума. QA smoke-драйвер стартует после закрытия экрана.

### Проверка отображаемого прогресса в Unity

LoadingRuntimeValidation проверен в реальном Editor Play Mode Unity 6000.6.5f1 при timeScale=0, с отдельными временными сохранениями. Файл progress.csv содержит отсчёты на реальных Time.frameCount: время, фактический прогресс, отображаемый прогресс, ReadyToClose. Для всех видимых кадров проверяются монотонность, отсутствие 100% до фактической готовности и минимального времени, отсутствие раннего 100% в целочисленной подписи. Пройдены холодный запуск, обычные переходы, ошибка/повтор/возврат и контрольные быстрый и долгий случаи.

Быстрый случай: фактическая работа занимает 0,2 с, экран закрывается через 1,031 с. Записано 62 кадра, 61 увеличение; максимальный шаг — 0,0206 (2,06 процентного пункта). При уже завершённой работе отображение составило 11,2% на 0,245 с; 40,6% на 0,496 с; 69,9% на 0,745 с; 87,5% на 0,895 с; 97,3% на 0,979 с. Значение 100% появилось только с ReadyToClose на 1,012 с.

Долгий случай: реальные отчёты равны 10% первые 1,2 с, затем 45%, затем 80%, завершение около 2,4 с. На 1,098 с показано 9,898% при фактических 10%; на 1,598 с — 42,948% при 45%; на 2,198 с — 77,570% при 80%. Проверено, что полоса не дрейфует к 99% после минимальной секунды, а следует реальным этапам и остаётся ниже 100% до их завершения. Экран закрылся за 2,449 с, без дополнительной секунды.

Исходники повторяемой проверки находятся в Tools; временные копии после прогона удалены из Assets. Плавность возможна только на реально отрисованных кадрах: неделимые Unity-операции (например PackTextures или GPU readback) всё ещё могут задержать кадр и требуют Profiler на устройстве. Standalone/Android/IL2CPP в этом прогоне не проверялись.
